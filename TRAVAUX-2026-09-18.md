# Travaux du 18/09/2026 — analyse du verrou GPU de la 4700S et test de flash BC-250

Compte rendu de ce qui a été fait, trouvé, et écarté. Complète [le journal](4700S-iGPU-journal_1.md) (section « Comparaison PSP / SMU / x86 »). Outils et images produits : `work/` du dépôt.

## Question posée au départ

L'image D (IgpuControl=1 + UMA 512 Mo) expose l'iGPU en `1002:13fd` mais l'îlot d'alimentation GPU reste éteint (GC/MMHUB/IH lisent `0xFFFFFFFF`) et le PMFW répond `0xFE UnknownCmd` à tout message GFX. Deux hypothèses restaient : **build PMFW différent** de la BC-250, ou **même binaire bridé** par un paramètre (fuse, ABL, APCB).

## Ce qui a été fait

### 1. Récupération et comparaison des images BIOS

Images réunies : dump réel de la carte (image D), C09 et C0A officiels AMD, et deux BIOS BC-250 repris de GitHub (`Robin5.00` de MrrZed0/bc-250-bios, `BC250_2.00.bin` de kenavru/BC-250).

psptool (pip) plante sur l'image 4700S (`TypeError` dans son parseur) : un parseur de répertoires PSP a été écrit pour l'occasion (`work/pspdir.py`, ~60 lignes, sort type/offset/taille/sha de chaque entrée des répertoires `$PSP`/`$BHD`).

### 2. Firmwares PSP : la réponse à la question de départ

| Entrée | 4700S (D / C09 / C0A) | BC-250 (2.00 / Robin5) |
|---|---|---|
| SMU_FW + SMU_FW2 | **70.16 / 70.17 / 70.18** | **88.6.0 / 88.7.1** |
| Clé de signature SMU | `b6f9ac22…` | `8b8df41e…` |
| ABL 0x30-0x34 | clé `c551a330…` | clé `663ca522…` |
| PSP_SECURE_OS | clé `8c77cdf9…`, tag **« CRD »** (Cardinal) | clé `5a3587b5…`, tag **« RBN »** (Robin) |
| PSP_BOOTLOADER | **« dummy binary »** (12 octets) → en ROM on-chip | 44 Ko réels en flash |

Deux résultats :

- **Le PMFW 4700S est un build sans GFX.** Même base de code que la BC-250 (chaînes initiales identiques, nom produit embarqué : `AMD 4700S 8-Core Processor Desktop Kit` vs `AMD BC-250`), mais **19 Ko de moins** (0x36439 contre 0x3add9 utiles). L'hypothèse « build différent » est la bonne.
- **Les deux puces n'ont pas la même chaîne de confiance.** Chaque bloc est signé par une clé différente, et le tag de plateforme diffère (CRD vs RBN). Sur la 4700S le bootloader PSP du flash est un bouchon : la première étape vient de la ROM interne. Transplanter SMU_FW seul était donc voué au rejet de signature.

`SMU_FW2` n'a aucune chaîne lisible (compressé ou chiffré) : non analysable statiquement. Le dispatcher des messages hôte n'a pas été retrouvé dans `SMU_FW` (recherche de tables de 64 pointeurs recoupée avec les ID qui répondent/ne répondent pas en vrai : aucune correspondance) — il est probablement dans `SMU_FW2`.

### 3. Côté x86 (AGESA) : aucun levier restant

Volumes UEFI extraits avec `uefi-firmware-parser`, modules identifiés par leurs sections UI, puis désassemblés (capstone). Les BIOS BC-250 sont des **builds debug** : chaînes de trace présentes, ce qui a permis de nommer les messages.

- Mailbox BIOS→SMU localisée : SMN `0x3B10528` (ID), `0x3B10564` (réponse), `0x3B10998-9AC` (6 arguments), service `NbioSmuServiceRequestV10`. Outil : `work/smucalls2.py` (trouve la fonction de service par la constante SMN, puis tous ses appelants et l'ID chargé dans `edx`).
- Messages envoyés par `AmdNbioSmuV10Dxe` : `0x05` EnableSmuFeatures, `0x2A` SetCoreTCtlMax, `0x17` DcBtc CPU des deux côtés ; **`0x2B` SetGfxTCtlMax et `0x18` DcBtc GFX côté BC-250 seulement**. Ce sont des messages de *configuration* : aucun code x86 n'allume l'îlot GPU, ni sur la BC-250 ni ailleurs. C'est le PMFW qui le fait de lui-même au boot.
- Le masque de features (`AllSmuFeatureControlDefines`) a été suivi jusqu'à ses PCD : tokens `0x120:0x121` (4700S) et `0x152:0x106` (BC-250). Base PCD EDK2 v6 décodée (`work/pcddb.py`, calibrée sur l'offset `0xE6A258` d'IgpuControl déjà connu) : **les deux masques valent 0 et personne ne les écrit** → pas un levier. Le bit 6, effacé quand IgpuControl=0, est déjà conservé par l'image D.
- Tailles révélatrices : `AmdNbioGfxARIPei` 6,7 Ko (4700S) contre 87 Ko (BC-250 debug) ; côté BC-250 ce module ne fait que l'UMA.

**Conclusion de l'analyse : le verrou restant est dans un firmware signé. Il n'existe plus de levier côté x86, PCD ou APCB.** Les deux leviers de ce type (IgpuControl, UMA) avaient déjà été trouvés et sont dans l'image D.

### 4. Vérification matérielle

Un relevé de tensions sur une carte 4700S (forum Badcaps) donne `TP_APU_VDDCR_GFX_RUN` à **0,83 V** : le VRM du GPU est monté et alimenté sur cette carte. Le blocage n'est pas une absence de composant.

### 5. Test : flash d'un BIOS BC-250 complet — échec

Seule piste restante sans matériel supplémentaire : faire tourner toute la chaîne RBN (dont le PMFW 88.x qui sait allumer le GPU). Risque annoncé et accepté : non-POST sans CH341A disponible.

Préparatifs : relecture fraîche de la puce (deux lectures identiques, `sha 3f2455d3…`, = image D + zones écrites à l'exécution) sauvegardée sur le Mac ; chemin de boot de secours `\EFI\BOOT\BOOTX64.EFI` vérifié ; journal systemd rendu persistant ; amdgpu laissé en blacklist.

Flash de `Robin5.00` avec flashrom (`-p internal -c W25Q128.V`) : écriture **VERIFIED**. Au redémarrage : **aucun POST**. Vérifié côté réseau (ping, balayage ARP des 254 adresses, recherche de la clé d'hôte SSH sur tout le LAN) : la carte n'est jamais revenue.

L'historique des boots (journal persistant activé juste avant) le confirme : tous les boots antérieurs portent la date BIOS 06/24/2021, le boot suivant porte 04/26/2022 (= C0A remis par toi le 04/10). **Aucun boot n'a eu lieu avec le BIOS BC-250.** Le silicium 4700S refuse la chaîne RBN — ce que la différence de clés laissait attendre.

## Bilan

| | |
|---|---|
| **Acquis** | Le PMFW 4700S est compilé sans GFX ; les deux puces ont des chaînes de clés distinctes (CRD vs RBN) ; aucun levier x86/PCD/APCB ne reste ; le VRM GPU de la carte est bon. |
| **Écarté définitivement** | Transplantation de SMU_FW/SMU_FW2 seuls (rejet de signature). Masque de features SMU (vaut 0, jamais écrit). Allumage par un message du BIOS x86 (n'existe pas). Flash d'un BIOS BC-250 complet (testé : pas de POST). |
| **Non testé** | `BC250_2.00.bin` (même rejet attendu, aucune raison de penser autrement). |

## Pistes pour une reprise

1. **Chercher un PMFW de la famille 70 qui contienne le GFX** — c'est-à-dire un firmware signé par la chaîne CRD, donc acceptable par cette puce : autres révisions 4700S (C06/C07/C08 restent à ouvrir avec `pspdir.py`, 30 secondes chacune), autres produits dérivés d'Ariel, kits 4800S. C'est la seule piste qui contourne la signature au lieu de s'y heurter.
2. **Reverse de `SMU_FW2`** (Xtensa, probablement compressé) pour trouver le dispatcher et la séquence d'allumage de l'îlot. Lourd, et sans moyen de modifier le firmware ensuite : utile seulement si l'allumage s'avère déclenchable depuis l'hôte par un message existant.
3. **Revenir à l'image D** (`work/bios/4700S_pre_flash_read_20260918.bin`, flashrom depuis Linux) pour retrouver l'état « iGPU visible + 512 Mo de VRAM » si on veut reprendre le travail côté amdgpu.

## Points de méthode retenus

- Toujours une lecture fraîche de la puce avant d'écrire : c'est elle qui contient les zones NV à jour, pas l'image d'origine.
- Journal systemd persistant avant toute manip de BIOS : c'est ce qui a permis de prouver après coup qu'aucun boot n'avait eu lieu.
- Chemin EFI de secours en place avant de changer de BIOS, sinon le nouveau firmware n'a aucune entrée de boot.
- Le flash est réversible depuis Linux **tant que la carte POST** ; dès qu'elle ne POST plus, il faut un CH341A. Ne pas refaire ce type de test sans le programmateur sous la main.
